# 将 Excel 数据追加到 DB_TABLE 数据集

用于把已确认的一份 Excel 转为分批 JSON，再通过 `lovrabet data batchCreate` 追加到一个 DB_TABLE 数据集。操作前确认本次新增范围；不默认更新、覆盖或删除已有记录。

`batchCreate` 每次只提交一个 JSON 批次，不读取 XLSX、不自动拆批，也没有导入检查点或 `--resume`。`data import-excel` 的检查点恢复仅适用于符合契约的 METADATA，不能用于 DB_TABLE。先按真实 `source` 选路；写入失败后不自动换入口。

## 1. 确认目标与执行条件

```bash
lovrabet dataset detail --appcode <appCode> --code <datasetCode> --format compress
lovrabet data batchCreate --help
```

确认目标为当前 User AK 可访问的已发布应用，详情中的 `source=DB_TABLE`，并核对：

- 字段 code、可写性、必填项、数据类型、长度、精度和枚举值。显示名称不作为 JSON 字段名。
- 自增主键、生成字段与默认值；默认不传这些字段，需要显式传入时以已确认写入契约为准。
- 能唯一定位每行的业务键，以及其数据库唯一约束或其他可靠去重契约。一个普通可查询字段不等于唯一键。
- 实际批量操作的可用性、条数/字节限制、返回格式、事务与失败语义，以及创建和回读权限。
- 关联字段、业务校验及 HOOK 的输入和副作用。详情未返回这些契约时，向用户或已确认的业务能力补齐；不以试写探测。

用户授权可以覆盖整个已确认导入范围，无须为每个既定批次重复请求授权。目标、字段或处理方式发生变化时，重新确认变化部分。

## 2. 转换整份文件，先处理数据问题

由 Agent 使用本地确定性脚本或现有工具解析工作表和表头，按字段映射生成 JSON 文件。保留原 Excel 的内容摘要、工作表、表头行、映射和源行号，输出逐行错误清单；不凭样例猜测剩余行。

| 输入 | 转换要求 |
|---|---|
| 文本、编号、电话 | 保留前导零，不擅自去空格或改大小写；Excel 已丢失的信息不能靠格式或猜测恢复 |
| 整数、金额 | 检查范围、精度、小数位；禁止 NaN、Infinity。超出 JavaScript 安全整数范围的编号保留十进制字符串，仅在接口明确接受时提交，避免先转浮点数 |
| 布尔、枚举 | 按实际接口所需类型和值提交；显示标签与存储值区分，不把任意非空文本当 true |
| 日期、时间 | 核对 Excel 日期系统、接口格式及业务时区；不把单元格序列数或本机时区推断直接当业务时间 |
| 空值 | 区分缺省字段、空字符串和 null；必填缺失先修正，是否触发默认值以写入契约为准 |
| 公式 | 使用已核对的计算结果；无缓存、缓存过期或依赖外部工作簿时停止确认，不上传公式文本代替结果 |
| 关联、附件、数组等复杂字段 | 使用真实关联 ID 和接口结构；无契约或无法解析时停止，不编造 ID 或把整个对象强转字符串 |

整份文件检查重复业务键、不可写字段、必填值和转换错误。发现重复时先确定“停止、跳过已有行或另行更新”的业务策略；普通新增不提供自动 upsert。错误未处理完不开始写入，除非用户明确批准可识别的部分范围。

以下仅为已确认字段后的批次结构示例，实际字段与值须来自目标契约和原文件：

```json
[
  {"order_no":"ORD-0001","customer_code":"C001","amount":125.5},
  {"order_no":"ORD-0002","customer_code":"C002","amount":80}
]
```

将当前批次保存为 `batch-0001.json`。也支持 `{"items":[...]}` 包装形式；不要把文件路径或 `@batch-0001.json` 当作 `--params` 的值。

## 3. 对账已有数据，确定批次

按已确认唯一键只读查询目标，记录写入前存在的键和 ID。存在内容不同的同键记录时报告冲突；已存在且相同的行按已确认策略处理，不能算成本次新增成功。没有可靠唯一键或结果定位契约时，先补齐，尤其不能承诺未知结果可自动重试。

- 同时满足服务端单批条数、JSON 序列化后的 UTF-8 请求体字节数和本机命令行参数长度限制。
- 不直接套用 METADATA `import-excel` 的 500 行限制；DB_TABLE 的上限来自目标实际契约，未知时先确认。
- 在已确认限制内生成固定、互不重叠的批次。每批记录源行范围、行数、业务键和内容摘要；执行后不重排、改写已发送批次。
- 单行超出上限时停止处理该行；不能靠继续减小批次解决，也不改用另一个写入 API。
- 默认串行推进；未核实一个批次的结果前，不继续后续批次。需要并发、跨数据集、原子提交或服务端幂等时，使用已发布且契约明确的业务能力。

## 4. 预览并执行当前批次

以下 Bash/zsh 示例将当前 JSON 文件内容作为一个参数传入；先完成上面的文件大小检查：

```bash
lovrabet data batchCreate --appcode <appCode> --code <datasetCode> \
  --params "$(cat "./batch-0001.json")" --dry-run --format compress
```

`--dry-run` 只解析参数并展示请求，不调用服务端写入，不校验数据库约束、业务规则或 HOOK，也不证明写权限已经通过。核对应用、数据集、当前批次数量和全部字段后，按已授权范围执行同一内容：

```bash
lovrabet data batchCreate --appcode <appCode> --code <datasetCode> \
  --params "$(cat "./batch-0001.json")" --format compress
```

Agent 调用进程时优先使用参数数组，并从文件读取 JSON；不要把单元格内容拼入 shell 命令。示例没有自动循环：每批先记录“即将提交”，保存实际退出码和响应，再按下一节回读。退出成功或 HTTP 成功本身不等于整批业务数据核验完成。

## 5. 回读，再推进下一批

使用实际返回的记录 ID，或已经确认的唯一业务键查询。例如下列字段必须确实存在，且已被确认是本次使用的唯一键：

```bash
lovrabet data filter --appcode <appCode> --code <datasetCode> \
  --params '{"where":{"order_no":{"$in":["ORD-0001","ORD-0002"]}},"select":["id","order_no","customer_code","amount"],"orderBy":[{"id":"asc"}],"currentPage":1,"pageSize":100}' \
  --format compress --jq '.data.result | {tableData,paging}'
```

`pageSize:100` 是查询示例，不是写入批次上限。先确认服务端返回的分页值和条件实际生效；结果超过一页时保持 where/select/orderBy/pageSize 不变，只递增 currentPage，直至完整读取。真实唯一主键不是 id 时，替换排序和查询字段；复合唯一键需要匹配完整组合。

逐行核对记录集合、数量、重复键和所有本次提交字段，按契约处理日期、精度、默认值等差异，不能把不一致自行归一化成成功。还要区分写入前已有记录与本次新记录；仅比较全表总量不能证明这批数据正确。

保留本地批次台账：原文件/映射摘要、目标和用户身份、批号、源行范围、内容摘要、实际请求时间、退出码、响应/回读 ID、结果和待处理项。台账由本次操作流程维护，**不是 CLI 内建检查点，不能传给 `--resume`**。不保存 AK；业务数据与台账保持私有访问权限。

## 6. 失败或结果不明时

| 现象 | 下一步 |
|---|---|
| 参数或字段校验失败，已明确未发请求 | 修正当前未发送批次，重新预览；保留失败记录 |
| 服务端拒绝、唯一约束冲突、部分成功 | 不假设整批回滚；按已确认事务语义和唯一键完整回读，区分已存在、新写入、冲突与未确认 |
| 超时、断连、响应格式异常 | 当前批次记为 unknown，暂停后续写入；先查询目标，不立即重发整个批次 |
| 回读为空或无权限 | 空结果不证明未写入；确认读取权限、数据可见范围、查询条件和一致性，无法确认则保留 unknown |
| 部分行已存在且与预期一致 | 保留实际 ID 和来源证据；只有能可靠确认其余行未写入、且满足重试授权/幂等条件时，才为这些行生成补写批次 |
| 同键内容不同或有重复记录 | 停止并交给业务负责人确定处理方式；不自动 update、delete 或更换业务键绕过冲突 |
| 限流或服务暂不可用 | 已发送写请求先对账；只有确认可安全重试后才按服务端要求退避，不把退避视为重试授权 |

未经确认的 DB_TABLE 原子性、幂等性和 HOOK 回滚能力不得假设存在。若业务必须可靠自动恢复、跨表依赖、upsert 或统一事务，使用已有可信业务服务/Backend Function；没有对应能力时停止并说明缺少的契约，不临时拼出另一条写入路线。

## 7. 向用户报告完成情况

报告目标、文件和批次数，以及“源数据行数、确认新增、原有跳过、失败、冲突、未知、尚未尝试”的数量；分类口径须可对账。给出实际记录 ID 或业务键与本地台账位置。只有全部拟写入数据已回读核实、未知与冲突均为 0，且跳过项符合已确认策略时，才能报告本次范围完成。

METADATA 的专用导入与检查点恢复见 [可恢复 Excel 导入](lovrabet-excel-import.md)；普通查询、分页和写入参数见 [Instant API 工作流](instant-api-workflow.md)。
